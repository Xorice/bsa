# 存档漏洞与资产一致性

按任务选择相关小节；每项都要联系真实入口、调用链和业务不变量。

## 一、把整份存档看作一个保存单元

装备、偏好设置、已读状态等看似低风险的字段，也可能与货币和库存保存在同一个 profile 中。某个字段不能序列化，影响可能扩展到整个 profile，而不只是该功能。

检查每个客户端可控的持久化字符串：

- **键与值都检查**：UTF-8 有效性、字节长度、业务白名单；不能只验证 `typeof(x) == "string"`。
- 动态槽名/字典键是否由服务端生成，是否允许无限新增；单字符串长度上限不能代替总条目数和整体大小预算。
- 所有写入分支，包括省略可选参数时的回退值。过滤显式 `slotKey` 后，实际键可能仍由客户端 `itemType` 生成。
- 仅用 nil 删除字典项不会新增持久化键；要证明新增风险，必须找到非 nil 值实际被写入的路径。
- 查表成功后写入服务端生成的固定数据，通常比原样复制请求安全；仍核对被保存的具体字段。

对表检查深度、数量、允许字段、键类型与值类型；对数字检查 NaN、正负无穷、业务范围及精度约束。JSONEncode 可辅助检查形状和估算大小，但不能单独作为 DataStore 接受数据的证明。

修复优先在业务入口收紧 schema 和允许值集合；在统一提交边界增加纵深校验。整体预算应为 profile 元数据和增长预留空间，不等于直接把平台极限写作业务上限。

## 二、从内存写入继续追到保存

识别 profile key、命名空间、加载/会话接口、定时保存、退出保存与关闭服务保存。核对：

- 加载失败是否拒绝业务，还是误将默认模板作为新存档写回。
- 数据何时可供请求使用；初始化/迁移失败是否仍放行或保存半成品。
- 持久化代理是真实校验还是仅类型提示、通知和内存赋值。
- 保存对象是否与修改对象为同一数据；快照、dirty 状态与成功确认的先后顺序。
- 保存失败、会话结束、服务器关闭后，是否仍能继续消费或转移资产。
- 失败重试是否有可恢复状态与观测；重试同一份不可保存的数据不能解决输入污染。

不要轻易改变成熟存档包；先检查业务调用错误和包的安装版本。单玩家会话所有权只能防止特定的过期写入，不会修复非法数据。

## 三、组合不同系统检查守恒

典型组合：`低风险写入口 → profile 无法保存 → 交易/摆摊正常变更 → 双方持久化结果不一致`。

区分三个层面：内存内的连续更新、单 key 的原子保存、跨 key 的可恢复结算。Luau 无 yield 的代码段可以避免部分交错，但服务器崩溃或某个 profile 保存失败仍然可能拆开两边的持久化结果。

业务不变量示例：

- 唯一物品完成转移后只有一个有效持有人；失败/恢复后也不能复制或消失。
- 货币转账保持总量扣除明确手续费后的守恒，不能出现一方已到账而另一方恢复旧余额。
- 奖励状态与奖励资产一起恢复，重放不会再发；失败不能永久标为已领却未发。
- 每份收据最多实际发放一次；确认已处理前具有足够的持久化交付证据。

跨玩家交易可以使用有持久化决策和恢复规则的事务日志/托管方案；具体设计取决于当前存储与业务。不能以“双方各调用一次 Save”宣称原子提交。

处理已污染的在线会话时，先限制对外转移并修复可保存性；随后根据明确提交结果处理会话。直接踢人可能触发失败的退出保存并留下回档窗口。不要把本轮正常交易的扣除盲目恢复到旧快照。

## 四、奖励和付费的幂等

找到服务器控制的 operationId / PurchaseId，核对去重记录的位置和寿命：

- 只在内存设 busy 能防部分并发，不能防重进或崩溃后的重放。
- 将发奖移出 UpdateAsync 回调能减少回调重试导致的副作用，但不代表整个收据处理只调用一次。
- 若持久化“已发放”与资产各在不同 key，检查两种顺序各自的故障窗口；业务发奖回调是否有独立幂等记录。
- 只有异常捕获成功，不能说明业务结果成功。核对 false/失败结果是否仍被标记成功。
- UpdateAsync 的变换函数可能再次执行，避免在其中消耗队列、发奖或调用外部有副作用的接口。

这类路径可列为进一步调查目标；未读所有回调、未验证故障窗口前，不应宣称已确认重复购买漏洞。

## 五、验证矩阵

|目标|隔离验证|判断依据|
|---|---|---|
|输入约束|正常值、未知槽、边界长度、无效编码、有限数边界|非法输入不改变状态；正常功能可完成|
|保存失败|适配器在指定阶段拒绝某个 profile 保存|无重复资产；状态可恢复；错误可定位|
|转移中断|在已存在的 yield 或持久化边界设置调度屏障|不凭空假设可交错；恢复满足唯一持有与守恒|
|奖励重放|相同 operationId 重复提交，模拟提交后回包丢失|最终只实际发放一次|
|会话失效|加载中离开、会话结束后回调继续、重新进入|旧任务不能修改新会话或释放后的存档|

记录 stub 的假设。例如内存存储器没有模拟 UTF-8、大小限制或云端重试，就只能证明逻辑行为，不能证明真实保存成功/失败。
