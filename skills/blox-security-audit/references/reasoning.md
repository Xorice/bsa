# 从正常交互推导漏洞

按机制选择 [surfaces.md](surfaces.md)；涉及持久化再读 [persistence.md](persistence.md)。目标是发现可破坏的业务约束，不是匹配危险函数或凑数量。

## 1. 先写不变量，再找破坏方式

为高价值操作写一行：`谁 / 什么状态 / 凭什么 / 对谁 / 改变什么 / 何时成功`。规则来自服务端实现、产品约定和测试；不明确就标待确认，不把自己的偏好当漏洞。

|边界|应回答的问题|可检查的不变量示例|
|---|---|---|
|权限|身份由哪里提供，授权针对哪个对象？|只修改本人拥有且当前可操作的物品；服务器确定发起者|
|价值|成本和收益分别从何处计算？|费用与奖励使用同一份可信配置；转移后唯一物品只有一个有效持有人|
|状态|操作在哪个阶段有效，旧请求何时失效？|已结束的比赛不能结算第二次；旧角色回调不能奖励新角色|
|持久化|哪些结果需要一起恢复，失败后如何继续？|领取消耗与奖励一致恢复；保存失败不会留下可重复转出的资产|
|资源|单次和累计工作由谁控制？|请求不能无界创建对象、增长存档或触发昂贵扇出|

写成可观察断言，如“成功或恢复后，物品编号在双方有效库存中的出现次数为 1”。金额守恒要扣除设计的手续费、产出和销毁。

## 2. 双向追踪，补齐真实链路

**从输入向前：**入口 → 包装层 → 身份/对象解析 → 校验 → 状态变更 → 回调/保存/外部副作用。

**从结果向后：**扣款、加物品、结算、保存、管理命令、外部请求等 sink → 所有调用者 → 可达入口与控制来源。两方向交汇以发现遗漏入口。

每步只记录改变信任或状态的事实：

- 输入是原样使用、归一化、查服务端表，还是服务器生成？标出键、值、路径、目标、数量和 operationId 的来源。
- 校验约束的是原始参数还是最终使用值？覆盖省略参数、默认值、别名、批量、旧协议、取消/退款等分支。
- 校验与使用指向同一对象、同一版本、同一会话吗？复制表、共享引用和缓存是否改变这一点？
- 防护是否在所有可达路径生效？类型标注、客户端按钮禁用、日志和 `pcall` 不能代替授权或回滚。

未补齐入口或影响的片段只记局部事实。不可达代码分别报告潜在启用风险与当前可利用性。

### 校验失败后还会发生什么

将 token、版本、身份、阶段或锁视为候选防护时，沿成功和失败分支追到实际副作用再判断。记录 `检查对象/代际 → 分支动作 → 被操作对象/代际 → 恢复结果`，包括 return 前的 cancel/reset、错误回调、finally 清理、异步任务和补偿；不能看到检查就标“被防护阻断”。

尤其检查跨 yield 后捕获的旧对象与当前共享对象是否一致。拒绝旧任务后直接返回，与拒绝旧任务却取消当前任务，保护效果不同；定时器 token 也不能自动保护绕过定时器的业务调用。对销毁/取消追踪资源的实际归属，删除容器不代表同时删除挂在其他父对象上的派生资源。

## 3. 用小型状态模型组合正常操作

把操作压缩为：`前置条件 → 读状态 → 改状态 → 成功依据 → 失败/恢复`。优先配对**共享资源或跨越同一边界**的操作。

|变换|要问什么|适用线索|
|---|---|---|
|次序|先 A 再 B 与先 B 再 A 是否仍守规则？|装备后出售、取消后确认、换队后领奖、配置刷新后退款|
|重复|同一意图多次到达是否只结算一次？|回包丢失重试、重复事件、收据重投、再次登录|
|替换|校验后被使用的对象/版本是否变了？|异步查价、加载资源、跨服查询、共享可变表|
|复用|多条输入是否实际上引用同一资源，计价与消耗的计数语义一致吗？|合成材料、批量出售、槽位、参与者；逐项归属合法不能证明整组合法|
|失效|退出、死亡、传送、结束后旧任务还能生效吗？|延迟奖励、计时器、Promise、事件连接、重用玩家缓存|
|中断|在一次已完成副作用之后失败，恢复是否安全？|先加奖后标记、先扣一方后加另一方、外部服务已成功但回包丢失|
|累计|每次合法的小操作是否突破整体预算？|自定义键、邮件、挂单、实例创建、全服广播、历史记录增长|

竞态必须标出**实际可交错点**：yield、异步回调、任务/事件调度、并行 Actor 或独立持久化提交，写出交错顺序与共享状态。没有 yield 的连续内存更新不能仅因“两个 Remote 同时来”就报竞态；也不能因此认定后续跨服/持久化提交原子。

## 4. 每个候选完成一次反证循环

使用紧凑候选卡，避免反复读全部源码：

```text
假设：哪个不变量可能被破坏？
前提：攻击者实际控制什么，入口/功能是否启用？
证据链：版本 + 函数/行号 + 输入变化 + 最终影响。
反证：最可能阻止此链的校验/锁/服务端重算/去重在哪里？成功与失败分支各操作哪个对象？
失败路径：具体失败时刻、已完成副作用、恢复行为。
最小验证：正常对照 + 触发分支 + 结果断言；隔离假设。
结论：按 validation.md 分类；区分代码缺陷、条件性影响及尚缺证据。
邻接推广：同类约束还在哪些入口或边界存在？
```

先找反证。检查已有防护能否经其他入口、默认值、批量、生命周期或失败恢复绕过；验证已否定候选就记录原因，转向下一项。

缺口成立后，按 [abuse-analysis.md](abuse-analysis.md) 再问“攻击者会拿它做什么”：将确定后果与项目已有交易、奖励、重连、取消等机制组合。对合理但未证实的高影响利用链，保留醒目的条件性提醒和补证任务；不因缺少最终复现而省略，也不把假设计作确认影响。

无发现时，输出已追踪链、不变量、起效防护和未验证条件。只能结论为“在此覆盖范围内未发现可证实漏洞”；用可复查的阴性证据解释依据，不保证任何情况下都安全。

## 5. 从一个问题推广到一类问题

把发现改写为机制：`不可信来源 → 缺失约束 → 共享边界 → 被破坏的不变量`，再搜索相同约束的其他实现。

- 动态装备键缺少约束 → 检查所有客户端可控持久化键，包括设置、收藏、命名、排序；同时检查最终回退键及累计条目数。
- 领奖去重只在内存 → 检查所有跨会话重放的发奖路径：任务、邮件、兑换、付费；比较去重记录和奖励的持久化边界。
- 校验后等待 → 检查相同对象在等待期间的出售、转移、解锁、销毁和换会话路径；检查恢复后的复核是否覆盖实际使用对象，以及失败分支是否误操作新状态。
- 接口接受目标对象 → 检查管理、交易、交互、伤害等“身份正确但对象范围错误”的入口。
- 批量校验与消耗不一致 → 检查所有列表到字典、数量到唯一实体的转换；按业务要求验证互异性或按重数计费，不把允许堆叠的设计一律判错。

不只搜索同名 API；查“共享 sink 的调用者”“同字段的写入者”“同状态的进入/退出边”。推广没有新增证据时停止扩散，说明覆盖范围。

## 安全负例：什么不足以证明漏洞

- 客户端发送价格，但服务器忽略并从配置重算：没有客户端定价漏洞；折扣、数量和扣款可另查。
- 复制到客户端的 ModuleScript 含数据 setter，但服务端没有暴露对应写方法：不能从客户端可调用推导服务端可写。
- 两次库存变更之间没有实际交错点：没有该内存竞态证据；是否存在保存失败窗口要另查。
- 服务器从本人库存将允许 itemId 映射为固定配置：与原样保存客户端表的风险不同。
- 未限流需结合可达成本、资源增长或重复执行，才能说明影响。
